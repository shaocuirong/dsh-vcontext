# v0.9.0：会话历史原位归档

用户需要移走已经进入 Harness 会话的旧聊天与工具结果。插件工作页归档只改变插件自身的注入快照；`compactNow` 虽能改变实际上下文，但会生成摘要。本版增加第三条路径：在宿主维护锁内，将**完整的旧轮次**通过原生 Session Surface 替换为一条短引用，不请求摘要模型。下一次真实 AgentLoop 请求因此不再携带这些旧消息的正文。

## 权威边界

原始事件日志保持不可变，仍是历史证据的权威来源；模型看到的是 Surface 投影。插件追加一条合法 `user/message` 替换事件，记录原节点的 `sourceEventSeqs` 与 `vctx://history/<会话哈希>/<事件序号>` 引用。没有直接修改 JSONL、删除原始事件、复制整个会话数据库，或声称改写已发送给供应商的过去请求。`history_read` 只允许在当前会话内按引用分段读取原始消息；读取产生新的普通工具结果，因此可能增加后续上下文。

归档只选当前 Surface 中连续的、已结束的旧轮次；最近两轮和 `system/developer` 消息受保护。一次最多 256 个模型可见节点、8 MiB 原消息正文；遇到宿主指令、已有归档引用或上限时，只在完整轮次边界结束。没有完整旧轮次时报告无候选，不假称减少了上下文。用户仍可单独选择大段读取结果做精确原位投影，或使用宿主摘要压缩。

归档是**按需检索恢复**，目前不是把多条消息按各自原始角色一次性恢复到原位。原始事件一直可由宿主回放，`history_read` 返回原始消息、类型和序号；引用本身不代表事实仍然有效、文件版本仍然相同，或任务已验证通过。未来若增加原位恢复，需要先解决多节点角色和工具配对的宿主格式约束。

## 操作流程与失败语义

1. 看板只读预览候选数量和字节；用户点击“归档旧聊天与工具结果”。
2. 宿主取得维护锁并先确认已有会话状态持久化，随后重新选择当前 Surface 的完整旧轮次。
3. 追加原生替换事件，持久化后读取实际前后消息数及字节数，记录不含正文的结构化诊断。
4. 发生并发变化、无候选或宿主不支持维护/持久化时明确失败。若提交是否成功不确定，先刷新实际上下文和宿主日志，不能盲目重复点击。

SQLite 无新增表或迁移；会话原文只在宿主日志，归档引用跨插件重启仍可从该日志定位。宿主日志不可用、被外部删除或损坏时，插件无法凭引用恢复内容。归档不自动触发，不在后台修改正在生成的会话。

## 研究依据

- [MemGPT](https://arxiv.org/abs/2310.08560)：把有限的模型窗口与可按需读取的外部历史分开；本版仅实现确定性换出和显式读取，不复现完整调度器。
- [Git Context Controller](https://arxiv.org/abs/2508.00031)：引用应指向确定的历史状态；本版使用宿主不可变事件序号，并不建立项目 Git 分支或文件 Commit。
- [SEEM](https://arxiv.org/abs/2601.06411)：来源序号与事件类型保留可追溯证据；本版没有事件图推理。
- [MAGE](https://arxiv.org/abs/2606.06090)：当前执行路径不能被旧失败证据误导；本版保留最近轮次，并依赖 v0.8 的任务状态注入，不实现自动 Maintain 策略。
- [ACE](https://arxiv.org/abs/2510.04618)：派生表示不能覆盖原始证据；本版甚至不生成摘要，原文始终以宿主日志为准。

具体的轮次保护数、容量上限与 Surface 协议是本项目工程选择，不宣称这些论文已验证该策略最优。完整文献见 [研究清单](RESEARCH.md)。
